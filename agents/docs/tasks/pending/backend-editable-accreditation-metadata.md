# Editable Accreditation Metadata + First-Accreditation Tenure Anchor

**Owner:** backend
**Created:** 2026-06-14

Make accreditation metadata (`name`/`institution`/`field`) editable post-accreditation by re-broadcasting an admin-signed `accredit` op carrying merged values, and introduce a first-accreditation tenure anchor so the displayed "accredited since" derives from the EARLIEST accredit op (all-history, across sanction gaps) rather than the latest op.

## Why

Today accreditation metadata is one-shot. The `accreditation.verify` existing-accreditation gate in `routes/accreditation.ts` (the `findExistingAccreditation` short-circuit) returns the prior `tx_id` WITHOUT re-broadcasting, so any new metadata captured at a second `/request → /verify` is silently discarded. The in-code docblock there explicitly flags that an updateable-metadata flow needs a paired design pass. ORCID-accredited accounts grant with empty `institution`/`field` (see `broadcastWotAccreditation` for the analogous WoT empty-field case) and have no path to fill them in.

Separately, every tenure-display consumer reads the LATEST accredit op's `event_timestamp` (the payload `timestamp` field). Once metadata edits re-broadcast a fresh accredit op, that payload timestamp is rewritten, so "accredited since" would jump to the edit time. The displayed tenure must anchor on the EARLIEST accredit op's CHAIN BLOCK TIME (not the payload `timestamp`, which a re-broadcast rewrites), counting all history across sanction gaps. Metadata reads stay on the latest op.

This is the canonical reference already written into `agents/docs/ARCHITECTURE.md` § 2 ("Accreditation Lifecycle & Sanctions") and the per-op fresh-auth requirement in § 6.4 / invariant #1 in § 6.5 — read those before implementing.

## Acceptance criteria

- [ ] **New authenticated edit endpoint** (e.g. `PATCH /api/accreditation/metadata`) accepting `{ full_name?, institution?, field? }`. Validate with the existing length bounds — reuse the per-field bounds from `accreditationRequestSchema` in `validation.ts` (`full_name` min 1 / max 200, `institution` min 1 / max 200, `field` min 1 / max 100); since all three are optional here, build a `.partial()`-style schema off those same bounds rather than duplicating the literals. Reject an all-empty body (no fields to merge).
- [ ] **Fresh re-auth proof required, NOT JWT-only.** Per ARCHITECTURE.md § 6.4 critical-action contract and § 6.5 invariant #1, this is a critical action (it triggers an admin-signed on-chain broadcast). It must demand a per-op fresh-auth proof appropriate to the account's auth mechanism via the `lib/fresh-auth.ts` machinery (`consumeFreshAuthToken` + a `FreshAuthTarget`). Add a new `FreshAuthTargetAction` member (e.g. `'edit_accreditation_metadata'`) to the `FreshAuthTargetAction` union and a target-builder helper modeled on `setPasswordFreshAuthTarget` (bind to the username so a proof minted for user A cannot edit user B). Pure self-custody users (no `accounts` row) satisfy the gate through the `verifyHiveSignature` per-request signature path; do NOT accept a bare JWT.
- [ ] **Guards before re-broadcast:** the account must be CURRENTLY accredited AND NOT sanctioned. Reuse the existing membership read (`getAccreditedSet` from `accreditation.ts`, or the `active_accreditations` CTE) for "currently accredited"; consult the sanction-status read once the sanction discriminator lands (see Coordination). If not currently accredited or sanctioned, reject (no broadcast).
- [ ] **Re-broadcast a MERGED admin-signed accredit op** via `broadcastAdminCustomJson` (`hive.ts`). Load the latest accredit op for the account (the `getAccreditationFromHaf` shape in `routes/profile.ts` is the reference read), overlay only the provided fields, and PRESERVE `method` and `orcid` from the prior op. Build an `AccreditAction` payload (`types/hive.ts`) — `action:"accredit"`, `account`, `name`, `institution`, `field`, `method`, `evidence_hash`, `timestamp` — and add the `issued_by` field per the settled design. NOTE FOR IMPLEMENTER: this is a self-service edit by the account owner, not an admin moderation action, so `issued_by` attribution differs from admin ops. Resolve the `issued_by` value here (the editing account's own username vs. a self-service marker) CONSISTENTLY with how `backend-admin-roster-and-authority-attribution` defines the `issued_by` shape — coordinate, do not invent a divergent convention. Carry `evidence_hash` forward from the prior op (do not fabricate a new one).
- [ ] **Replace the "metadata one-shot" gate in `routes/accreditation.ts`.** The `findExistingAccreditation` short-circuit in `accreditation.verify` currently returns the prior `tx_id` without re-broadcasting and discards new metadata (the `existing_accreditation_hit` branch). Decide and implement: either (a) route metadata changes exclusively through the new `PATCH` endpoint and keep `/verify` idempotent for the email-confirm path, OR (b) have the gate-hit branch re-broadcast with merged metadata. Prefer (a) — a dedicated edit endpoint with its own fresh-auth proof — but in either case, UPDATE the stale "Profile metadata is one-shot at first /verify; the gate-hit discard is intentional" docblock so it no longer claims one-shot semantics. Anchor any new comments on behavioral semantics, not task slugs/round numbers/line numbers.
- [ ] **First-accreditation tenure anchor.** Add a per-account EARLIEST-accredit derivation: `MIN(cj.block_num)` over `action='accredit'` rows for the account (filtered by `config.accreditationAuthorities` and `custom_id = config.appTag`, same signer/app gate as `activeAccreditationsCteBody`), joined to block time to yield a chain-block-time value. Count ALL accredit history across sanction gaps (do NOT reset the anchor on a revoke/sanction). Expose as a distinct field, e.g. `first_accredited_at` / `accredited_since`. Preserve the BitmapAnd-avoidance rule documented on `activeAccreditationsCteBody` (no `block_num >= genesis` floor on the custom_json scan). Source the block timestamp from a block-time join, not from the payload `timestamp` (a re-broadcast rewrites the payload).
- [ ] **Re-point tenure DISPLAY consumers to the anchor, keep latest-op for metadata.** The "accredited since" display must read the anchor; metadata (name/institution/field/method/orcid) must keep reading the latest op:
  - `getAccreditationFromHaf` (`routes/profile.ts`): keep returning latest-op metadata; add the `first_accredited_at` anchor field for the "since" display.
  - `routes/accreditations.ts` STATUS route (`fetchAccreditationStatusFromHaf`): expose the anchor alongside the latest-op `timestamp`.
  - `routes/accreditations.ts` LIST route (`fetchAccreditationsFromHaf`): currently `ORDER BY timestamp DESC` on the latest-op payload `timestamp`. Give the anchor ITS OWN field so the sort semantics do NOT silently change — the list keeps sorting by the existing latest-op `timestamp` field unless we deliberately change the contract; only the displayed "since" reads the anchor. Do NOT repurpose the existing `timestamp` field.
  - Frontend: `frontend/src/pages/profile.js` (the `profile.accreditedVia` binding renders `formatDate(profile.accreditation.timestamp)`) and `frontend/src/pages/accreditation.js` (the `formatDate(accreditation.timestamp)` `<dd>`) must render the new anchor field for "accredited since" while leaving metadata fields on the latest op. Coordinate the field name with whatever the backend status/profile envelopes expose.
- [ ] **Keep the `accounts` DB columns in sync.** On a successful edit broadcast, update the `accounts` row's `full_name`, `institution`, `field` columns (all three exist per `migrations/001_schema.sql`) to the merged values so the runtime cache matches the chain (chain stays SSoT; the table is a rebuildable cache). For pure self-custody users with no `accounts` row, skip the DB write (no row to sync) — the chain read covers them.
- [ ] **Tests, real-path where feasible** per the project test conventions in `CLAUDE.md` ("Running Tests" / the carve-out). Cover: the edit endpoint rejecting a bare JWT (real `verifyHiveSignature` / fresh-auth gate — this test's focus IS auth, so do NOT mock the signature/fresh-auth middleware); merged-metadata broadcast preserving `method`/`orcid`; the currently-accredited and not-sanctioned guards rejecting ineligible accounts; the tenure anchor returning the EARLIEST block time and surviving a re-broadcast (latest-op `timestamp` moves, anchor does not); and the list-route sort field staying on the latest-op `timestamp`. Mocked-pool route tests, if used, must follow the documented HAF-route recipe (genesis-block→0 + complete redis mock) and the carve-out header requirements.

## Implementation notes

- The latest-op metadata read already exists in three places with the same signer/app filter (`getAccreditationFromHaf` in `profile.ts`, `fetchAccreditationStatusFromHaf` + `fetchAccreditationsFromHaf` in `accreditations.ts`, and the `activeAccreditationsCteBody`/`active_accreditations` CTE in `hafsql.ts`). The anchor is an ADDITIVE per-account `MIN(block_num)` aggregate over the SAME accredit rows — factor it as a small composable CTE/select alongside the membership CTEs rather than duplicating the signer filter inline.
- `RevokeAction` (`types/hive.ts`) currently has no `type` discriminator; the sanction-aware "not sanctioned" guard depends on the `type:"sanction"` discriminator and sanction-status read that `backend-revoke-sanction-wot-membership` introduces. If that task has not landed when this one is implemented, gate on "currently accredited" only and leave a behavioral-anchored TODO for the sanction check (do NOT cite the sibling task by slug in code comments — task slugs rot on archive).
- Do not widen the on-chain signer. All authority ops remain signed by the single `config.pevoAdminPostingKey` via `broadcastAdminCustomJson`; the edit endpoint is a human-authorization layer in front of that key.

## Coordination

- **Shares `hafsql.ts` membership/anchor CTEs with `backend-revoke-sanction-wot-membership`.** That task touches `activeAccreditationsCteBody` / `accreditationStatusCteBody` / `activeVouchesCteBody` for the sanction discriminator and live-threshold WoT membership; this task adds the first-accreditation `MIN(block_num)` anchor over the same accredit rows. Both edit the same WITH-block region — sequence to avoid clobbering, and keep the anchor CTE additive so it composes with the sanction-status CTE rather than forking the signer/app filter.
- **`issued_by` attribution shape is shared with `backend-admin-roster-and-authority-attribution`.** Every authority op's payload gains `issued_by`. Admin ops attribute the acting admin; this self-service metadata edit attributes the account owner (not an admin moderation action). Use the SAME `issued_by` field name and value convention that the admin-roster task establishes; do not invent a divergent shape. If that task defines a system/self-service marker convention, reuse it here.
