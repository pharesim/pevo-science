# Reclassify revoke as authority sanction; live-threshold WoT membership; ever-sanctioned guard

**Owner:** backend
**Created:** 2026-06-14

The `revoke` authority op currently does double duty: it is broadcast both as a deliberate moderator action AND automatically whenever a WoT member's vouch count drops below threshold (`buildRevocationPayload` carries the fixed reason `"WoT threshold no longer met"`). This conflates a sticky punishment with ordinary loss of standing, and there is no sanction-history check anywhere — a sanctioned account can be silently re-accredited by the WoT auto-path the moment its vouch graph recovers.

This task makes `revoke` mean **sanction only**, makes WoT membership **live-threshold-gated** (self-healing, no revoke broadcast on threshold drop), adds the **ever-sanctioned guard** to the WoT auto-accreditation path, and treats all **legacy revokes as non-sanctions**. Per ARCHITECTURE.md § 2 "Accreditation Lifecycle & Sanctions" (already written), a `revoke` is now a deliberate authority sanction; threshold drops are handled by live membership evaluation with no `revoke` op.

## Why

- A WoT threshold drop is reversible standing, not a punishment. Broadcasting a sticky `revoke` for it (and cascading) wrote a permanent-looking suppression for what is really a transient graph state, and required a fragile cascade with timeout budgets to undo. Live evaluation self-heals with zero broadcasts.
- A true sanction must be sticky: it suppresses membership regardless of vouch support, and the only lift is a deliberate authority `accredit`. Without a `type:"sanction"` discriminator there is no way to distinguish the two, and without an ever-sanctioned check the WoT auto-path re-accredits a sanctioned account behind the moderator's back (the KNOWN GAP in `broadcastWotAccreditation`).

Remove/replace `revokeVoucheeIfBelowThreshold` (`backend/src/wot.ts`) so the retract-vouch route handler (`backend/src/routes/wot.ts`, the `revokeVoucheeIfBelowThreshold(status)` call after `pollForRetraction`) no longer broadcasts a revocation; the route's `revocation_outcome` branch should collapse to a "no action needed, membership self-heals" response. Authority-pinned methods (`email`/`orcid`/`manual`) stay accredited by their latest `accredit` op and are NOT threshold-gated. Touch points:
  - `activeAccreditationsCteBody` (`backend/src/hafsql.ts`): WoT rows must join `active_vouches` (via `activeVouchesCteBody`) and survive only at-or-above threshold; non-WoT rows pass through on latest-`accredit`-wins as today.

  - Membership semantics for the sanction discriminator: a `method='wot'` row whose latest action is a `type:"sanction"` `revoke` is suppressed (sticky); a `method='wot'` row whose latest action is a **legacy** `revoke` (no `type:"sanction"`) is NOT suppressed and falls through to live threshold evaluation against its prior `accredit`.
- [ ] **Legacy revoke handling.** Any `revoke` lacking `type:"sanction"` (all historical revokes, reason `"WoT threshold no longer met"`) is a non-sanction and is **ignored for stickiness**. Only `type:"sanction"` revokes suppress membership. Concretely, the `accred_ranked`/`ranked` latest-action logic must NOT treat a legacy `revoke` as a membership-killing terminal state for a WoT account — it reverts to live threshold; for an authority-pinned account, a legacy revoke similarly does not stick (membership reverts to its latest `accredit`). Keep `accreditationStatusCteBody`'s audit `'revoked'` status semantics intact for the forged-ORCID audit path (that CTE is additive and audit-only), but ensure membership consumers no longer key off bare `action='revoke'`.

## Implementation notes

- `activeAccreditationsCteBody` and `getAccreditedSet` both inline near-identical `accred_ranked`/`ranked` SQL but are NOT shared — both must get the WoT-vs-authority split. Consider whether the WoT-threshold join can live in one shared fragment to avoid drift, but do not block on the refactor.
- The sanction discriminator lives in the op `json` payload (`cj.json::jsonb ->> 'type'`), so the CTE `WHERE` / `CASE` logic reads it alongside `action`/`method`. Legacy rows return SQL `NULL` for `->> 'type'`, which is exactly the non-sanction case.
- `getAllEverAccreditedOrcidsWithStatus` / `accreditationStatusCteBody` are audit-path (forged-ORCID visibility), not membership — leave their `'active'`/`'revoked'` status semantics alone; only membership consumers change.
- Verify no remaining production caller of `buildRevocationPayload` before deleting it; the only callers today are `cascadeRevocation` and `revokeVoucheeIfBelowThreshold`, both removed/replaced here.

**Design note — authority-pinned = non-wot.** The membership filter uses `method IS DISTINCT FROM 'wot'` for the authority arm rather than the literal `method IN ('email','orcid','manual')`.
